### Наш путь (эволюция)

**`rag_1/code_rag` — BM25 RAG, Qwen** *(самый первый прототип)*
- BM25-поиск по 590 страницам, топ-12 → Qwen через OpenRouter
- Никаких source_pages в ответе — G был ужасным, модель не указывала источники
- 100 вопросов warm-up фазы

**`rag_1/solve_rag.py` — BM25 RAG v2, Qwen**
- То же самое, но добавили source_pages в JSON ответе
- Стало лучше по G, но retrieval всё ещё только BM25

**`rag_1/code_hybrid` — Hybrid BM25 + Semantic, Qwen** *(первый гибрид)*
- Добавили семантические эмбеддинги `text-embedding-3-large` через OpenRouter
- RRF объединение, TOP_K=10
- Закэшированный embed_cache_hybrid.npy (6.9MB)
- Всё ещё Qwen — дешёвый, но не точный

**`code_archive_grok6` — Hybrid + Grok dual-model** *(переломный момент)*
- Та же BM25+Semantic+RRF архитектура
- Смена модели: Grok `grok-4-1-fast-reasoning` (для boolean/name/names) + `grok-4-1-fast-non-reasoning` (для остального)
- Прямой xAI API вместо OpenRouter — меньше латентность, лучше F
- Эмбеддинги по-прежнему через OpenRouter (xAI не даёт embeddings)
- Это стало базой финального решения

---

### ChatGPT подход (`chatgpt/`)

**GPT-5.2 + OpenAI Vector Store** *(совершенно другая парадигма)*
- Каждый PDF разбивается на отдельные одностраничные PDF файлы
- Все страницы загружаются в **OpenAI Vector Store** (нативный)
- Поиск через `client.vector_stores.search()` — OpenAI ищет сам
- Ответ генерирует GPT-5.2
- Интересный подход: работа с PDF напрямую, без конвертации в текст
- Минус: полная зависимость от OpenAI инфраструктуры, дорогой Vector Store

---

### Qwen CAG (`qwen-cag/`)

**Context-As-Gold: все 30 документов в один промпт** *(радикальный подход)*
- Никакого retrieval — все документы сразу в системный промпт (~350K токенов)
- Qwen через OpenRouter
- Идея: раз у Qwen миллионный контекст — зачем RAG?
- Плюс: модель видит всё, нет ошибок retrieval
- Минус: TTFT огромный, дорого, F score убивает длинный контекст

---

### Morag подход (`morag/`)

**Production RAG на локальном железе** *(самый инженерный)*
- **Qdrant** как векторная база данных (локальный сервер)
- **Sparse + Dense embeddings** — два отдельных HTTP-сервиса:
  - Dense: `http://localhost:8082` (float embeddings с MD5-хэшем для sparse)
  - Sparse: `http://localhost:8081` (BM25-like token weights)
- **LLM через Ollama**: `qwen2.5:7b` локально — нулевые затраты на токены
- Три отдельные модели: LLM, filter-model (50 токенов для фильтрации), intent-model
- Фильтрация по намерению перед retrieval (`intent_model`)
- chunks_used в ответе (вместо source_pages)
- Самый сложный пайплайн из всех, но локальный и дешёвый
- Финальный результат: **0.603** (S_asst = 0.760 — лучший free_text!)

## Часть 1: построить машину

Соревнование пришло неожиданно — **30 юридических документов DIFC Courts** (Дубайский международный финансовый центр), 900 вопросов, и нужно было отвечать точно. Судебные решения, законы, нормативные акты, консультационные бумаги — всё на юридическом английском, с артикулями, датами, номерами дел, суммами в AED и USD.

Первый подход казался элегантным: запихнуть все 30 документов в системный промпт (~350K токенов) и спросить у большой модели. Qwen через OpenRouter. Работало, но было медленно и дорого. Ведь говорят некторые - CAG - это будущее. 

Потом вернулись к классике: **hybrid RAG**. BM25 + семантические эмбеддинги (Gemini), объединённые через RRF. Каждый вопрос — быстрый поиск по 4057 страницам, топ-15 страниц в контекст, и Grok отвечает уже с конкретными цитатами.

Но RAG — это не просто "поищи похожее". Нужно было понять специфику:
- Вопрос "В деле CFI 035/2025..." — нужна именно первая страница этого дела, которая даёт контекст
- Вопрос про "fee for exemption application" — нужен именно Schedule 1 Regulations, а не любая страница где встречается слово "fee"
- Вопрос "какой закон был принят позже" — нужны обложки обоих законов

Так появились **Pinning Maps** — детерминированные правила, которые принудительно добавляют нужные страницы поверх того, что нашёл retriever. CASE_PAGE1_MAP, LAW_PAGE1_MAP, REG_SCHEDULE_MAP, DOC_PAGES_INDEX. Каждая — результат анализа конкретных провалов. Спасибо, Клод.

Тогда пришла идея **золотого сета** - где собрать полностью выверенные ответы. Сначала с этим просто помог Клод. Спасибо, Клод.

Warm-up фаза: 10 попыток. Лучший результат — **v15, 0.780, 45 место в итоге**. Казалось — вот оно. Но впереди была финальная фаза.

## Часть 2: война с метриками

Финал. 900 вопросов, 2 сабмита. Никаких ошибок.

Сначала перевели в md. convert_fast.py — двухрежимная конвертация:

1. Обычные PDF (с текстом) → pymupdf4llm

Библиотека вытаскивает текст напрямую из PDF структуры
Быстро, без API, бесплатно
Каждая страница оборачивается в <!-- page:N --> маркер

2. Сканы (avg < 50 символов/страницу) → qwen3.5-9b vision через OpenRouter

Детектируется автоматически: если текста почти нет — значит скан
Каждая страница рендерится в PNG (150 DPI через PyMuPDF/fitz)
PNG в base64 → LLM → Markdown
Медленнее и платно, но точно

Плюс: fallback — если pymupdf4llm падает, используется fitz.get_text("text") напрямую.

**Чанки для эмбеддингов, но страницы в контекст**

Семантический поиск требует эмбеддингов, и здесь было нетривиальное решение.

Проблема: страницы юридических документов бывают очень длинными — до 10–15 тысяч символов. Модель эмбеддингов gemini-embedding-001 имеет ограничение на входной текст (~2000 токенов). Если нарезать страницы на чанки и эмбеддить чанки — поиск будет точнее. Но LLM нужно отдать целую страницу, а не половину: юридический контекст нельзя рвать.

Решение — parent-page retrieval:

Каждая страница разбивается на чанки по 6000 символов (~2000 токенов) с перекрытием 200 символов
Каждый чанк получает свой эмбеддинг.
При поиске — ищем по чанкам, но возвращаем родительскую страницу целиком.
Технически: массив chunk_to_page хранит индекс родительской страницы для каждого чанка. Нашли топ-K чанков → дедуплицировали по странице → отдали модели целые страницы.

4102 чанка из 4057 страниц (большинство страниц помещались в один чанк, длинные делились на 2–3). Кэшировалось в .npy файл — не пересчитывать при каждом запуске.

**Решили сделать супер золотой сет**

После модели из warm-up, запустили verify_v2.py — многошаговую верификацию: структурная проверка, проверка правдоподобности через LLM, перепроверка по документам. Grok, потом Gemini-3.1-Pro-preview (до 18 долл за мил, с полным кешированием нужных документов - т.к. контекст 1 мил - что в 10 раз снижает стоимость!), читали страницы и говории: "да, это правда" или "нет, вот что там написано на самом деле". 606 gold / 198 uncertain / 96 wrong из первого прогона. Итерировали снова и снова, исправляли золото вручную, пока не стало 900/900.

Первое что сделали — разобрали 34 неправильных детерминированных ответа. Некоторые были смешными: модель возвращала `['GTC TRADING S.A.']` вместо `['GTC Trading SA']` — одни и те же буквы, но разный регистр и точки. 

Нашли реальные проблемы с gold: вопрос "когда был выдан документ SCT 475/2024" — gold говорил `2024-01-20`, но в документе явно написано **"Date of Issue: 2 April 2025"**. Исправили. Consultation Paper по Data Protection — gold говорил "Data Protection", но документ называл это "Data Protection Law". Исправили.

Заодно навели порядок в папке с кодом — убрали мусор, инициализировали git, начали версионировать. Теперь каждое изменение — коммит. (Т.к. поняли, что надо было однажды откатиться к прошлому варианту...)

**v6** — исправления промптов, ограничение ENF в CASE_PAGE1_MAP (один документ вместо четырёх — ENF дела часто связаны с другими и затягивали не тот контекст).

**v7** — большая итерация. Убрали нормализацию names (regex убивал "R.E." → "RE", а gold ждал точек). Исправили артефакт "(162 chars)" — модель считала символы для самопроверки и добавляла аннотацию в ответ. Починили обрезку длинных free_text ответов через JSON truncation fallback.

Прогнали sample: 90 вопросов. Eval показал: **S_asst = 0.7815** — free_text заработал. Но полный v7 дал Total ≈ **0.733**. G упал с 0.9436 до 0.8725 — модель начала цитировать страницу 2 вместо страницы 1 для "date of issue" вопросов. Проблема в том, что на странице 2 написано явно "Date of Issue: 2 April 2025", а gold ожидает страницу 1 где та же дата в заголовке.

F тоже просел — reasoning модель для boolean/name/names даёт TTFT 7-8 секунд, среднее по прогону 6024ms. При F-формуле это больно.

Начали эксперименты.

**v8**: убрали reasoning ВЕЗДЕ — пусть всё non-reasoning, зато F = **0.9919** (средний TTFT 3168ms). Красиво. Но S_det рухнул до **0.8884**: boolean упал с 100% до 83.4%, name с 92.6% до 83.2%, names с 95.6% до 80%. Non-reasoning модель просто не справляется с логическими задачами. Total ≈ 0.721. Это Грок, дешевый и быстрый, наш любимчик.

**v9**: reasoning для ВСЕГО кроме free_text — может дата и number тоже выиграют? Ожидание было. Реальность — names провалился до **80%** (было 95.6% в v7!), хотя reasoning был включён. Почему? Возможно промпт "cite page 1 for date questions", который мы добавили в v8/v9, как-то запутал модель при обработке names. Total ≈ 0.695 — худший результат.

Вывод, написанный болью трёх прогонов по 900 вопросов и ~$18 токенов:

> **v7 был лучшим. Reasoning только для boolean/name/names. Non-reasoning для date/number/free_text. Не трогать.**

## Локальный eval — как мы не сжигали сабмиты вслепую

У соревнования был лимит: 10 сабмитов в warm-up, 2 в финале. Тратить слоты вслепую — ну мы потратили на warm-up за день до конца.

Поэтому мы построили **собственный eval app** — некий клон официального скорера, работающий локально. Он считает все метрики до отправки на лидерборд.

**Стек:** Gradio UI + scorer.py + judge.py + gold_answers_final.json

Загружаешь `submission.json` → через ~2 минуты видишь:
- S_det по каждому типу (boolean/date/number/name/names) с таблицей correct/wrong
- S_asst: LLM судья (Grok) оценивает каждый free_text по 5 критериям
- G: grounding score с разбивкой по вопросам — какие документы/страницы совпали
- Итоговый Total

**Задеплоили на сервер** (https://manzherok.ru/eval/, чтобы вы полюбовались) — чтобы иметь доступ с любого устройства, хотя и на локальном тоже можно.

**Ключевая роль в процессе:** каждая версия кода (v6, v7, v8, v9) сначала прогонялась через локальный eval. Разбирались кейсы, eavl позволяет смотреть страницы и сырые pdf и md.

Парадокс: локальный eval показывал v7 Total ≈ 0.733, а официальный дал 0.631. Разница — в том, что наш gold set был построен из наших же ответов (с ошибками). **Eval не врал — он измерял именно то, что ему дали.**

Исходный код: https://github.com/catonmoon/legal-rag-lb

## Финальный ход

Один сабмит остался.

Пришла идея: у нас есть **верифицированный gold set** — 900 ответов, которые мы строили своими руками через многошаговую верификацию. Это наши данные, наш труд. У нас есть v4 submission с отличным G = **0.9436** и хорошим F — лучшая grounding из всех версий.

Объединяем: берём ответы из gold set, телеметрию (refs, timing) из v4. Получаем **submission_final_gold_v4.json** — 900 ответов, только 9 None (там где gold тоже не знал ответа).

Перед этим отправили submission Morag — его файл через наш API ключ, с его zip-архивом. UUID `6fd62914`. Первый финальный слот.

Второй финальный слот — наш gold+v4. UUID `8a09eeb4`.

Оба ушли в очередь. Ждём лидерборда.

## Что узнали

**Технически:**
- Non-reasoning модель неприменима для логических типов (boolean/name/names) — теряешь 10-17% accuracy
- G score чувствителен к номеру страницы: одна и та же информация на стр.1 vs стр.2 даёт G=0
- BM25 + Semantic RRF работает хорошо, но pinning maps решают многие случаи лучше
- Чанкинг для эмбеддингов + возврат целых страниц — правильный подход
- Верификация ответов через LLM ("re-ask from docs") — мощный инструмент для построения gold

**По соревнованию:**
- F-фактор TTFT бьёт сильно: разница между 2s и 7s TTFT — это 1.02 vs 0.92 множитель
- G с β=2.5 (recall-heavy) — при правильных документах extra страницы не убивают, но неправильный документ = G=0
- free_text S_asst оказался стабильнее чем думали — 0.78 держится вне зависимости от длины инструкций

**Человеческое:**
- Соревновательный азарт реален: когда eval показывает 0.721 в 2 часа ночи — это боль
- Итерировать быстро важнее чем итерировать правильно с первого раза
- Gold set, построенный с нуля — это актив. Он позволил понять, где дрорабатываться.
